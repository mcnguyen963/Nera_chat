# B9 — recover changing token counts during context construction

Implemented 2026-10-08. Files changed: `js/memory-context.js`, `tests/memory.mjs`. Backups retained under `production-backups/B9/`; no git used.

A mismatch between incremental part costs and the finalized request now rebuilds the context exactly once. The rebuild creates fresh local part/message cost caches. If the rebuilt result still disagrees, the context is returned using the actual finalized wire-request count, and the report contains a warning. Successful recovery is also reported. The legitimate input-limit guard remains enforced against the actual final count.

The shared token counter was inspected: fallback counts are not retained when tokenizerReady=false. A recovered tokenizer's cached counts are valid, so no shared-cache changes or cache flush are needed for this failure mode.

Regression coverage: one counter changes after 40 calls then stabilizes; one changes on every call. Both return a context and warnings; the latter verifies the returned usedTokens against the exact sequence of counter values observed while counting the finalized messages, not a later recount. Both tests fail with `Context cost accounting mismatch` against the backed-up original implementation in an isolated temporary tree and pass after the fix.

Tests before: full suite 343 tests, 342 pass, 1 fail (concurrent L3 tolerant grammar changes). After: focused memory plus legacy golden 69/69; full suite 347 tests, 346 pass, same unrelated L3 grammar assertion failure. JavaScript syntax check passes. Root owns final suite integration while other tasks continue.

Firestore reads/writes: 0 added per turn. LLM calls: unchanged, at most 2 per turn. The retry only assembles an in-memory request; it does not load Firestore or invoke the provider. No Firestore write path touched, so no new halfway-save failure behavior. No deployed/provider/device check performed for this task.
