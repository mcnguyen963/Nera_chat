# D9 — deleting the latest reply preserves its turn on Retry

Changed: js/messages.js, tests/message-chunks.mjs. Existing original backups retained.

Deleting an assistant discovers later chunks and checks the session revision inside the delete transaction before trusting that discovery. The transaction reads later chunks and resets nextNarratorTurn to the removed reply's narratorTurn only when there is no later assistant. Trailing summaries do not prevent the reset. Older assistant deletions preserve the counter.

Regression tests: focused suite before 43/43, after 45/45. The new delete→Retry test fails before the fix and checks matching persisted narratorTurn, computeTurns pairing, and dueRange including both the user's action and replacement reply. A second test protects the counter when a newer assistant exists in another chunk. Concurrent full-suite snapshot: 343 tests, 338 pass; five unrelated in-progress D3/parser failures were reported to root.

Read impact: normal sends unchanged. User-initiated assistant deletion adds one server session read to capture the discovery revision, a later-chunk query (one read per returned chunk, with Firestore minimum query charge), and a transaction read per distinct later chunk beyond the target. Non-assistant deletion unchanged. Writes unchanged: reset shares the existing atomic session write. LLM calls unchanged.

On a concurrent history change or database failure, the transaction commits no deletion or counter reset and the existing delete handler shows the error; the user may retry after refreshing. No partial turn-number change is possible. No browser/live Firestore verification claimed.
